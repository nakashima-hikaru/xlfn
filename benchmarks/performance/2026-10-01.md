# Borrowed inputs and shared coordination, 2026-10-01

Four remaining costs identified in the performance review were changed:

- Formula preparation of `MatrixRef<f64>` validates and hashes the borrowed
  cells before lookup, then copies typed values into call scratch only when
  materialization is needed. Resource-free built-in element types opt into
  this path. Strings, custom preparation, wrappers, and plain input conversion
  keep their existing eager policy.
- An ordinary nonfinal object pin release completes while holding the
  capability-transition lock. A serial pin acquire/release cycle takes two
  arena mutex acquisitions instead of three. Final release still retains an
  active-release guard through payload destruction and notifications outside
  the lock. Test/refinement observation retains its conservative release tail.
- Pending cache flights use 32 hash-selected, padded coordination locks.
  Equal versioned keys select the same lock, preserving singleflight across
  threads and keeping old/new epochs separate. The resident index remains
  Quick Cache with one shard and the same global weight budget.
- Module callback admission uses the existing kernel striped drain counters.
  A close/reopen mutex is used only for transitions. Close publishes rejection
  before sealing stripes; admission checks the phase both before and after
  reservation. Result cleanup keeps the owned permit through `xlFree`, even
  when another thread performs that cleanup.

These changes preserve per-cell validation, input budgets, identity framing,
conversion/error order, final-release ownership, and invocation-local callback
terminal statuses. A warm formula hit still scans the input contents; this
change removes the typed scratch copy from its borrowed numeric input stage.

changing baseline production code. The candidate is the uncommitted working

the system allocator, macOS arm64, SDK 15.2, and an Apple M1 with eight CPUs.
Separate target directories were used; compilation and verification finished
before timed measurements. Frozen executable hashes and source provenance are
in [2026-10-01-paired.json](2026-10-01-paired.json).

samples per case per round. The table reports the median of each

including means and their 95% confidence intervals. This is a short local

Borrowed preparation/discard models the input stage of a warm lookup. It
includes raw ingress, validation, identity finalization and call-scope cleanup;
it does not execute a formula cache lookup or a UDF. Preparation/materialization
models the corresponding input work on a miss. Deferred copying introduces a
second numeric conversion pass on that path, explaining the measured cold
regression. The allocation savings and repeated-input improvement justify this
tradeoff for producers that reuse their formula results. A workload dominated
by cold calls should remeasure this tradeoff with its expected hit rate.

Pin batches include dispatch, a simultaneous-start barrier and completion
coordination, with worker creation excluded. Final-pin setup and arena cleanup
are excluded; the timed final release includes payload destruction. Production
measurements omit the `refinement` feature so the ordinary unobserved release
path is selected; regression tests also explicitly exercise that path.

Cache batches use fresh distinct keys or a shared key per request index, a
fixed 1 MiB resident budget, and 4,096-element numeric reductions. Clear,
start-channel sends and correctness probes are outside timing; the start
barrier, cache operations and completion coordination are inside. Same-key
rows include pending followers and resident reuse by later arrivals. Batch
request counts grow with worker count; they are not per-request latency.

Caller resolution uses a deterministic callback stub through production host
callback admission and result cleanup. Concurrent batches include dispatch,
the start barrier, resolution, cleanup and completion; worker creation and
stub setup are excluded. Each worker owns its own callback session. These
figures measure framework coordination with a stub, not calls into live Excel.

Controls were retained rather than subtracted. At four workers, object
dispatch changed from 22.95 to 23.35 µs (+1.8%), and caller dispatch from
21.54 to 21.48 µs (-0.3%). Cache compute-only controls use the same worker
topology. Numeric controls changed by at most 1.3%; the 32-worker cheap
distinct-key control rose 5.6%, illustrating scheduler noise. Cache dispatch
controls were not selected by this comparison's filter. At 16 and 32 workers
the eight-CPU host is oversubscribed. Remaining resident-index, allocation,
reclamation and scheduling costs prevent a claim of linear scaling.

Warm cache controls also completed: one-worker cases improved by 8.9–13.1%,
while 32-worker cases changed by -0.3% to -2.2%. They exercise resident lookup,
read-domain admission and cache-node pin release, bypassing flight coordination.
Their observed differences do not isolate a changed production hot path.
Plain/scalar/text controls and small borrowed inputs remain in the complete
JSON; the largest text-control increase was 0.8%. These observations do not
establish universal speedups.

## Allocation and capacity

The independent probe runs 100 calls per borrowed numeric case. Requested
bytes are allocation traffic, not peak live memory or RSS. Fixture allocation
is excluded. [2026-10-01-probes.json](2026-10-01-probes.json) retains final
executable hashes, complete output and cache-policy comparisons.

| Input stage, per call | Baseline requests / bytes | Candidate requests / bytes |
| --- | ---: | ---: |
| Borrowed 1k numbers, prepare identity | 2 / 14,200 | 1 / 6,024 |
| Borrowed 100k numbers, prepare identity | 2 / 808,824 | 1 / 6,024 |
| Borrowed 100k numbers, prepare and materialize | 2 / 808,824 | 2 / 808,824 |

The candidate has an absolute regression gate for warm 100k-cell preparation
(at most two requests and 16 KiB requested per call), plus absolute and
one-versus-eight-argument identity-workspace checks. Scalar and handle ingress
probes still require zero allocations.

Flight coordination adds one constructor allocation and 4,048 bytes per cache
on this arm64 layout: the old 64-byte table becomes a 16-byte registry plus
4,096 bytes of padded shard storage. Per-shard maps allocate lazily. This
changes coordination storage; it does not partition resident capacity.
Fourteen deterministic cold/repeat cache-policy rows match exactly in request
counts, computes, computed payload bytes, resident entries/weight, pending
node counts, peak pending nodes/weight and hit rate. Post-clear reclamation
checks also passed. Index metadata estimates are diagnostic and are excluded
from this policy-equivalence comparison.

## Reproduction

These historical commands require a Rust 1.98.1 checkout through
`b9596f8e221ef3804bb802c0795d7e7e8660f8df`. The current checkout requires
Rust 1.99; use the [Rust 1.99 comparison](rust-1.99.md) for the current tree.
Use a fresh output directory. SDK 15.2 is the recorded macOS workaround;
use the appropriate native SDK on other hosts and retain those results as
a separate comparison.

```sh

rtk proxy sh -c 'git archive 87e540f3958f3a7cab327b3c9450373dab0e19c4 | tar -x -C target/performance-repro-20261001/baseline'
```
